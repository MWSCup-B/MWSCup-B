# 事件報告書・調査資料・被害原因の設計（2026-09-28）

作業ブランチは `kanematsu-work`。本変更は、ゲームの被害原因を証拠から再構成するという利用者要求に基づく。既存の疑似コマンド、サーバー別の調査画面、保存値の共有、証拠の保存と法廷の完了条件、独立検証ゲートは維持する。

## 画面

- Scenario Previewの接続線はサブネット背景より上、ノードより下に描く。設定された接続をすべて描き、通信許可・禁止と接続の存在は区別する。ノードの文字列は日本語・長い英数字も折り返し、文字数に合わせた高さとSVG文字幅を指定する。図のスクロールは図の領域内に限定する。
- 事件ファイル → 事件報告書 → 調査・争点01の順に表示する。報告書では争点一覧・場面転換・台詞演出を表示しない。
- 報告書は「被害の概要」「被告人に対する嫌疑と根拠」「提出資料」「関係者の供述」。検察側の主張を技術的事実として断定せず、攻略案内の定型文は入れない。保存済みの報告書でも指定された旧定型文は表示時に除く。原証拠は変更しない。
- 「資料・結果」は撤去する。法廷で既存資料を再読する機能は法廷パネルに残す。ヘッダー・争点一覧は固定したまま、報告書と調査本文が必要に応じてスクロールする。

## 新しく生成する事件

攻撃選択APIの設定に `incidentDesign: ATTACK_CAUSED_HARM_V1` を記録する。新しい前提・被害・取得条件を `incident-design.js` で定義し、従来と同じAttack Graph検証へ渡す。旧設定にこのプロファイルを暗黙に追加しない。選択されていない攻撃、OS権限、ネットワーク経路は追加しない。プレビューの制作詳細に条件を表示する。

| 攻撃 | 具体的な被害 | 調査で比較するもの |
| --- | --- | --- |
| Stored XSS | 閲覧者の認証済みセッションで、同一サービスに虚偽の告知が自動投稿される | 保存投稿、後の閲覧要求、スクリプト実行記録、通信の開始元、投稿APIの受理 |
| SQLインジェクション | アプリのDB主体が読める非公開レコードが、Web応答で要求元へ返却される | Web要求、実行SQL、要求IDとクエリIDの対応、返却対象の参照またはダイジェスト |

Stored XSSでCookie窃取・管理者権限を仮定しない。通信の開始元・スクリプト実行は事件前から有効な記録を取得し、アクセス履歴やCSP違反ログで代用しない。SQLインジェクションを単なる投稿閲覧で成立させず、入力によるSQL構造の改変とDB側権限・返却条件を確認する。OSコマンド実行は追加しない。

真相は内部の `groundTruth.incidentNarratives` に先に確定する。攻撃主体と被告人は教材内で別の役割として定義する。公開資料では「被告人が直接行った」とされる処理と別の発生原因を比較する。単に意図を証明できないという結末へ戻さず、攻撃で被害が生じた経路を示す。ただし、IPやアカウントから人物の実名を同定したことにはしない。未定義のアリバイ・供述・人物対応を生成して不足を補わない。

SQLの旧モデルでは、statement欄で保証された構造改変と要求・実行の対応だけを問い、特定の検索範囲・検索件数・漏えいを推定しない。新モデルの被害返却は追加した明示条件と取得資料に基づく。

## ログと検証

生成するWeb・DB・認証・アプリ・通信ログは各100件以上の異なる記録を必須とする。生成目安は100～120件。通常処理を既存の取得条件内で含め、事件の記録を時系列の途中に置く。本文は製品を特定しないJSON Linesとし、英語の記録値を使用する。教材説明、正解、人物評価はログ本文へ入れない。報告書・供述・設問・解説は日本語のままとする。

証拠およびゲーム資料の本文上限は100,000文字。ハッシュを付ける前の生成出力を検証し、封印後に行を水増ししない。件数・形式の不足は既存の最大2回のEvidence修正へ返す。

生成draftは事件の原記録と、資料ごとの通常処理例`logBackgrounds`（3～8例）を分ける。通常例は同じ取得元・取得項目の範囲に限り、既存の時刻・処理識別子だけを変えて100件まで展開する。時刻のタイムゾーン・小数桁の表記を維持し、事件の位置は資料によって変える。事件の原文を前後の通常記録の間に保持し、原文のバイト列・引用を維持する。固定行番号の取得操作は位置を補正し、全文を読む操作は展開後の全文を読む。原記録の不足・因果の不一致を通常例で補って合格にしない。修正時もコンパクトなdraftを渡し、100行の再出力を繰り返さない。

表示用語は「ブラウザのスクリプト実行記録」「ブラウザの動作記録」に統一する。生成された表示名・設問・調査手順に旧表記が出た場合も修正へ返し、封印済みの原文や引用を後から置換しない。

同じ攻撃内の対応を検証する。Stored XSSは保存投稿・閲覧・実行・発行要求・投稿受理を照合する。SQLは要求IDとクエリIDの**同じ組**が実行・成功応答にあることを確認し、無関係な行から各IDを拾って結び付けない。これは構造と参照の検査であり、スクリプトやSQLの意味を実行して判定しない。内容の技術的成立性、人物への帰属、反駁の解答可能性に関する独立レビューを維持する。

画面の改善は保存済みゲームにも適用する。被害・ログ・証拠・法廷の新しい内容は再生成が必要。

技術資料：[OWASP XSS](https://community.owasp.org/attacks/xss/)、[OWASP SQL Injection](https://community.owasp.org/attacks/SQL_Injection)、[Chrome DevTools Network reference](https://developer.chrome.com/docs/devtools/network/reference)。これらは攻撃や観測の一般的な意味を説明する資料で、教材内の被告人の行動を立証する資料ではない。
