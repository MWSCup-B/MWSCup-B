# 攻撃の段階別選択とカタログ拡張

変更日：2026-09-20。目的：任意の攻撃1件から複数件を選び、技術条件を保ったまま多様な事件を作成する。

## 原因

1. UIの選択一覧はカタログ順で、解除した攻撃の後続に古いOrderが残った。選択数に関係なくOrderは1～3しか選べなかった。
2. テンプレートのOrder・時刻にもカタログ位置を使用していた。後ろの攻撃を単独で選ぶとOrderが1にならず、種類の追加で分の値が60以上になる実装だった。
3. Author側がGraphの単一連結を要求していた。各攻撃が技術的に成立していても、独立成分を含む組合せを拒否していた。
4. 証拠取得元は4種類のartifact IDに固定され、Web・メール以外を追加できなかった。シナリオの比較文もWebリクエストを前提にしていた。
5. 攻撃数の上限はUIだけでなくCandidate、Graph、Timeline、学習目標等に重複して存在していた。

## 修正

- 初動・誘導／侵入・外部からの悪用／実行／権限昇格／侵入後・情報収集で絞り込み可能。フィルター変更で他段階の選択を消さない。すべての段階を埋める必要はない。
- 攻撃の選択・解除時に選択済みのOrderを1から振り直す。追加した攻撃は選択順に並べ、初期時刻を残っている攻撃より後へ設定する。明示的な順番変更では編集済み時刻を保持し、確認を促す。
- 1～6件を全契約で受理する。6件の上限は全実行順の評価を最大6!＝720通りに制限するため。未登録攻撃、重複、0件、7件以上は拒否する。
- 独立成分を含むGraphを受理する。因果辺は前段の効果と後段の前提の対象・条件が一致した場合だけ作る。選択順と因果関係を区別する。
- 初期権限等が前段から得られない単独攻撃では、それを教材の開始条件として明示する。開始条件の説明は攻撃内容画面で確認可能で、生成入力のScenario ContextとGraphにも保持する。未選択の侵入方法を追加しない。選択した前段効果が必要な場合、その効果を開始時点へ繰り上げない。
- 新しいartifactには取得元Binding・記録種別・証拠種別・取得対象種別を定義できる。既存4種類の取得定義には互換性を残した。
- 対象OS、全Role、サービス所属、到達性、取得元のログ種別を検証する。構成に合わない攻撃では先頭のNodeを暗黙に選ばず、対応テンプレートを案内する。
- 既存の画面遷移・承認・独立レビュー・証拠検証・最終評価は維持する。検証失敗を警告に格下げしない。
- プロンプトの旧コード保存コメントは送信前に除外し、AIに旧指示と新指示を混在させない。

## 攻撃と構成

既存のフィッシング、反射型XSS、SQLインジェクションに次の6種類を追加し、合計9種類とした。

| 攻撃 | 成立条件・効果の範囲 |
| --- | --- |
| 有効アカウント悪用（SSH） | 認証情報と要求される認証・認可条件が揃い、一般ユーザーのシェル起動が許可される場合。rootを付与しない。 |
| パストラバーサル | 入力を使うファイル参照の制限不備と、アプリケーションの対象ファイル読み取り・応答条件が必要。コード実行へ拡張しない。 |
| sudo設定不備 | 一般ユーザーとして実行可能で、rootへの危険なsudo許可と認証条件が満たされる場合。 |
| setuid設定不備 | 一般ユーザーが実行可能な安全でないsetuid rootプログラムと、setuidが実効制御で抑止されない条件が必要。 |
| Windowsサービス実行ファイルの権限不備 | 書換え可能な実行ファイル、LocalSystemのサービス設定、書換え後の起動、実効制御の許可が必要。再起動権限やドメイン権限を自動付与しない。 |
| 保護ファイル収集（Linux） | 開始時または前段でroot実行権限を取得済みで、対象データも読み取り可能な場合。外部送信は含まない。 |

追加テンプレート：`data/networks/enterprise-lab.json`。「Web・SSH・権限昇格の教材構成」をSubnet画面で明示的に適用する。既存構成は自動変更しない。新しいService Typeの`local_execution`はホスト上の実行環境を表し、通信リスナーの存在を意味しない。

例：SQLインジェクション単独／sudo単独／XSS＋SQLの独立攻撃／SSH→sudo→保護ファイル収集／SSH→setuid→保護ファイル収集。

## 検証

- `node --test`：374件中373件成功。残る1件は既存の `tests/generation.test.js` のWindowsシンボリックリンク作成で発生する`EPERM`。検証を無効化せず残した。
- 新規テストは9種類すべての単独生成、独立攻撃、sudo／setuid連鎖、6攻撃を、モックAIによる承認・証拠生成・ゲーム構築・最終評価まで検証した。
- 必要条件と選択順が矛盾する場合、OS不一致、到達不能、証拠取得元の不足、件数制約も検証した。
- UIは初期フィッシングの解除、後方の攻撃だけの送信、フィルター変更、順番変更、解除後の追加時刻をDOMテストで確認した。
- 全体テスト後の日時調整を含め、攻撃選択・UIの対象テスト36件も成功。最後に旧プロンプト指示の除外を個別検証した。
- 既存テストにあった「個別のWeb観測要件を残しながら全4目的で不足する」というfixtureの不整合も修正した。全Web根拠を削除するケースとして検証を維持した。
- 実Codexログインによる生成や生成文の品質評価は未実施。モック通し検証は実AIの審査結果を保証するものではない。
