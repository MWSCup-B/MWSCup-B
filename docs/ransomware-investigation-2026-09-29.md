# ランサムウェアの調査資料と操作

2026-09-29の利用者要求に基づき、新規生成のランサムウェアを5種類の資料から調べる構成へ変更した。生成可能性と検証済みの攻撃経路を維持し、SSH認証は必須にしない。現在の自動構成はWindows端末であり、単独時は明示した初期実行条件、複合時は選択したClickFix等の結果を使用する。

| 資料 | 調べる内容 |
| --- | --- |
| ファイル操作ログ | 時刻、アカウント、PID、実行ファイル、操作、対象パス。通常時と被害時間帯の件数を比較し、対象PIDの書込み・改名・要求文作成を時系列で確認する。 |
| 被害ファイル | 元の対象識別子、実形式、SHA-256、先頭バイト、読取り可否。拡張子を実形式と同一視しない。 |
| バックアップから取得した元ファイル | 攻撃前に保全された正常版の同じ検査項目。新しいサーバーやバックアップ破壊・復元操作は追加しない。 |
| 身代金要求文 | 使用不能化、復旧への金銭要求、架空の連絡方法が書かれた保存本文。本文は書き手の主張として扱う。 |
| プロセス実行ログ | 実行日時、アカウント、PID、親PID、実行ファイル、非実行の教材コマンドライン。対象と直接の親の記録を照合し、さらに上位は保存記録がある範囲だけ追跡する。 |

`process_ref` / `parent_ref`は相関ID、`pid` / `parent_pid`はOSの番号として分離した。PIDの再利用や別端末の同じ番号を誤って結ばないよう、端末・時刻・相関IDも検証する。ClickFixの既存の相関IDをPIDと呼ばない。

既存WorkspaceのTemplateに、期間を指定したPID・実行ファイル・操作別の件数集計と、指定PIDの時系列表示を追加した。コマンドは固定された資料文字列だけを処理し、OS・Shell・ファイル本体・証拠内の命令を実行しない。集計の出力だけでは原文の証拠保存にならず、対応する行を閲覧して明示保存する。

被害側と正常版はどちらから調べてもよい。両方の対応する行を閲覧すると、既存Viewer内に形式・ハッシュ・先頭データの比較を表示する。未閲覧の行、別端末・別ファイル、対応が一意でない行は表示しない。比較表示だけで証拠を自動取得しない。複数の比較は一つの領域内でスクロールする。

9月28日のWorkspace方式を維持し、操作の4択を必須の通過画面として再導入しない。利用者の選択肢案は、生成する`materialInvestigations`の調査目的・読み解き例・誤読例として使う。集計はWorkspaceの疑似コマンド、読み解き例は既存の行表示・文字列検索で実際に確認できる内容にする。操作回数をそろえるために資料や実行経路を捏造しない。

検察側の最終主張は、被告人のアカウントでプログラムが動いたことを本人の意図的な破壊と同一視するものとした。操作の集中、内容変化、使用不能化、要求文を組み合わせて被害を判断し、その処理と人物・意図の帰属を区別する。最終争点にはClickFix等の前段の取得済み資料も保持する。ハッシュ差や形式不明だけで暗号化方式を断定しない。

生成時は資料の由来に加え、同じ攻撃の正常版と被害側、実行・書込み・改名・検査の順序、直接の親、要求文の作成を照合する。不備は既存の最大2回の証拠生成へ差し戻し、解消しない資料はビルドへ渡さない。Importが不成立でも段階別の根拠不足を同時に収集し、最後の試行まで別の不備を隠さない。旧保存ゲームの本文・正解・保存形式は書き換えず、新しい資料構成は再生成時に適用する。

技術説明の確認先：一般ファイルの暗号化・改名・金銭要求は[MITRE ATT&CK T1486](https://attack.mitre.org/techniques/T1486/)、プロセス生成監査のPID・実行ファイル・コマンドラインの記録条件は[Microsoftのイベント4688資料](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4688)を確認した。今回の資料は事前に設定した専用の合成記録であり、Windowsの既定ログに全項目が必ず残るとは扱わない。

## 2026-09-30：各ログを100件程度へ拡充

利用者の追加要求により、ファイル操作ログと同じ攻撃ノードのプロセス実行ログは、無関係な通常記録を含めて各100件以上にする。通常の新規生成では100件まで展開する。被害ファイル・正常版・要求文の件数は増やさず、ClickFixなど別の攻撃ノードの同名資料へこの条件を広げない。

生成AIは事件・比較用の原記録と各ログ3～8件の通常例を出力し、Backendがハッシュ付与前に100件へ展開する。元の記録・引用を文字列のまま保全し、行表示の参照位置も追従させる。通常例は同じ端末・取得項目を使い、既存事件のPID・相関ID・対象パスの再利用を拒否する。通常例の資料間で同じプロセスを参照するときは、PID・実行ファイル・アカウント・親子関係・時刻順序を維持して複製する。追加記録は事件と直前の比較用記録の時間範囲から離し、元の期間集計を変えない。

100件不足や不正な通常例は既存の証拠生成リトライへ差し戻す。事件の成立性は展開前の原記録で確認し、追加記録で必須証拠の欠落を補完しない。旧保存ゲームは変更せず、再生成したゲームへ適用する。

追加修正の検証：関連42件は全件成功し、100件化後の期間集計・PID検索・原文引用・行表示・通常処理の親子関係・ゲーム完了を確認した。全体テストは640件中639件成功し、残る1件は上記変更と無関係なWindows向けCodex起動テストで、ローカルの`@openai/codex`依存が未導入のため失敗した。

ClickFixとの複合構成の実AI検証では、対象外のClickFixログへの展開指示と、65桁のSHA-256が同時に含まれる失敗を捕捉した。通常記録のエラーだけで元資料の不備を隠さず、最初の試行で両方を差し戻すようにした。対象外のevidenceId、ハッシュの対象ファイルと必要桁数を明示し、既存の最大2回の生成内で修正させる。検証条件の緩和やハッシュの自動切詰めは行わない。

実AIのランサムウェア単独・会社構成は、初回独立検証と初回Evidence生成で`READY` / `ACCEPTED` / `ACQUITTED`になった（約429秒）。ファイル操作ログは原記録8件＋通常記録92件、プロセス実行ログは原記録3件＋通常記録97件で、どちらも100件の異なる記録を確認した。事件PIDの検索結果と全設問の引用が展開前の原記録から変わらないことも確認した。

今回のClickFix→ランサムウェアの新規実AI生成は、上記の65桁のハッシュが再試行にも残り`FAILED`となった。捕捉した失敗データへ2つの不備を同時に返した実AI再現検証でも、そのハッシュは未修正だった。不正な検査値のままゲームを完成させてはいない。

件数変更との切り分けとして、9月29日に実AIで`ACCEPTED`になったClickFix→ランサムウェアの資料を、通常例を加えた各100件のログとして再生検証した。新しいテストセッションの参照IDに結び直し、レビューをモックにした通常パイプラインで、元の公開ログ・事件PIDの検索結果を保ったまま`READY` / `ACCEPTED` / `ACQUITTED`を確認した。これは既存の実生成データを使った回帰検証であり、新規の実AI生成成功とは区別する。
